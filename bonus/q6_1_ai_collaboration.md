## 2. 我的第一个 prompt 是什么？AI 的回答有什么问题？

**第一版 prompt（大意）**：
> "用 pandas 写一个函数，把退货单（InvoiceNo 以 C 开头、Quantity 为负）匹配回对应的原始销售记录，
> 同样的 CustomerID 和 StockCode 就匹配。"

**AI 第一版的问题**：
- 直接 `df.merge(on=['customer_id','stock_code'])`，把退货行和所有同名正向销售**逐行笛卡尔展开**，
  既慢（百万行爆炸）又错误（会把多条正向销售都算作匹配，丢失"数量对应"与"时间最近"约束）。
- 没有处理 `|Quantity|` 必须等于原单数量这一关键条件。
- 对"匹配不到"的情况没有日志，无法审计。

## 3. 我迭代了几轮？关键修正点

共迭代约 4 轮，关键修正：
1. **加数量约束**：匹配必须满足 `正向 quantity == |退货 quantity|`，否则是不同批次。
2. **加时间约束 + 取最近**：候选必须 `invoice_date < 退货日期`，且取"时间上最近的一笔"（closest preceding）。
3. **改结构避免笛卡尔**：先按 `(customer_id, stock_code)` 建索引字典，只在退货子集上做循环
   （退货行数远小于全表），避免 `iterrows` 全表扫描（满足题目性能要求）。
4. **补日志与断言**：匹配不到记 `NULL` 并统计未命中数，写入 `pipeline_log.txt`。

## 4. AI 的最终答案有什么错误或不足？我怎么发现并修正的？

- **错误**：AI 初版会「匹配到多条」且不分先后，`merge` 之后同一笔退货对应十几条候选，`matched_original_invoice` 变成一列多值。
  我用一组**合成边界用例**发现它：同一客户同一商品分两次退、原单数量小于退货数量、退货日期早于原单。
  修法是候选按时间升序、取最后一个命中（即最近的前序销售）。
- **不足（也是我最终推翻了 AI 建议的地方）**：AI 和我都曾倾向把规则放宽成
  「原单数量 ≥ 退货数量即可匹配」，理由是「买 10 退 5 应该能配上，匹配率能到八成」。
  但动手前我先算了一下放宽会波及多少条：未匹配的 12,674 条里有 **9,636 条（76%）是「买过但数量对不上」**，
  放宽规则等于把这 9,636 条全部配到一笔金额不同的原单上——**匹配率上去了，但每一条都可能是错的**。
  退货分析的下游是「哪些商品被退回、退了多少钱」，错配一条就多算一笔退款，误差会直接进业务报表。
  所以最终坚持严格相等（宁可 65% 不匹配），并把未匹配的部分**逐层归因**写进
  `validation_report.md` 3.3.1——把「配不上」从缺陷变成了结论。
  这个判断是我做的，不是 AI 给的：AI 只提了「可以提高匹配率」，没提「提高的同时会污染多少条」。

## 5. 如果再做一次，我的第一个 prompt 会怎么写？

> "写一个退货匹配函数。输入：退货明细（C 开头、qty<0）与真实销售明细。
> 匹配规则必须同时满足：(a) 同 customer_id 与 stock_code；(b) 正向 quantity == abs(退货 quantity)；
> (c) 正向 invoice_date 早于退货日期；取时间最近的一笔。匹配不到返回 NULL 并计数。
> 性能上禁止全表 iterrows，用 groupby/字典索引，只在退货子集上循环。
> 请给出带断言校验与日志的实现。"

——**先给约束、再要实现**，比"帮我写个匹配"质量高一个量级，AI 一次就能逼近可用版本。
