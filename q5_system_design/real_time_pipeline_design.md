# Q5 实时数据管道设计（real_time_pipeline_design.md）

> 场景：Olist 从离线 CSV 升级为实时架构。卖家要在订单状态变更 30s 内看到、评价进来 1min 内触发情感+LLM 抽取、物流异常自动报警、历史 6 个月成交曲线毫秒级响应。规模：10 万单/天，2 年内涨到 100 万单/天。

---

## 一、整体架构图（ASCII）

```
┌────────────┐   CDC / 业务事件    ┌──────────────┐   发布事件    ┌─────────────┐
│ 订单/交易   │ ─────────────────▶ │  消息队列     │ ────────────▶ │  流处理       │
│ 系统(OLTP) │                    │  Kafka       │               │  Flink/      │
└────────────┘                    └──────────────┘               │  Spark SS    │
                                                                 └──────┬─────┘
        ┌──────────────────────────────────────────────────────────┘
        │ 按事件类型分流
        ▼                                  ▼                         ▼
┌──────────────┐                  ┌──────────────┐        ┌──────────────────┐
│ 订单状态变更  │                  │ 评价文本流入   │        │ 物流时效监控      │
│ → 写缓存/推送 │                  │ → 情感分析+LLM │        │ → 延迟判定→报警   │
│  (Redis+WS)  │                  │  (异步队列)    │        │                  │
└──────┬───────┘                  └──────┬───────┘        └──────────────────┘
       │                                  │
       │ 落库                             │ 结果写回
       ▼                                  ▼
┌──────────────┐                  ┌──────────────┐
│ OLTP(订单库) │                  │ 向量/ES(评价) │
│ MySQL/PG     │                  │ 供检索聚合    │
└──────┬───────┘                  └──────────────┘
       │ 定时/CDC 同步
       ▼
┌──────────────┐   查询加速     ┌──────────────┐
│ OLAP(ClickHouse)│ ◀────────── │  卖家后台 API │
│ 历史成交/曲线  │   预聚合物化视图│  (读缓存优先) │
└──────────────┘                └──────────────┘
```

**数据流向一句话**：业务系统产生事件 → Kafka 解耦 → Flink 做实时计算与分流 →
订单态进 Redis（卖家实时看板）+ MySQL（权威库）；评价进 LLM 异步抽取后入 ES；
物流时效独立监控并报警；MySQL 经 CDC 同步到 ClickHouse 供历史分析，卖家查历史走预聚合。

## 二、数据存储选型与理由

| 数据 | 选型 | 为什么 |
|------|------|--------|
| 订单/交易主数据、状态 | **OLTP：MySQL 8.0 / PostgreSQL** | 需要强一致、事务、点查（按 order_id 查），是权威源 |
| 实时事件流 | **消息队列：Kafka** | 解耦生产端与消费端，削峰、可重放、支持 30s 内送达 |
| 卖家实时看板热点数据 | **缓存：Redis** | 订单状态变更后写 Redis，卖家后台订阅 WebSocket 直接读，满足 30s 内、高并发低延迟 |
| 评价抽取结果、全文检索 | **Elasticsearch** | 支持按 category/severity 聚合与全文检索，便于产品改进看板 |
| 历史成交曲线（6 个月） | **OLAP：ClickHouse / Doris** | 列式存储 + 预聚合物化视图，毫秒级响应亿级行聚合，远胜 MySQL |
| 原始日志/抽取原文 | **对象存储：S3/OSS** | 低成本归档，供审计与模型回溯 |

**关键原则**：OLTP 管"当前真相"，OLAP 管"历史分析"，MQ 管"实时流转"，缓存管"热读"。
层级分明，互不拖累——历史查询再重也不会拖垮下单事务。

## 三、LLM 成本失控如何避免（含量化估算）

若「每条评价都过 LLM」：规模 100 万单/天，假设约 20% 有评价 ≈ **20 万条评价/天**。
按 gpt-4o-mini 估算单条 ~1k 输入 + 300 输出 token ≈ $0.00033/条：
**20 万 × $0.00033 × 365 ≈ $24,090/年**。若用 gpt-4o 则约 $130k/年，显然不可接受。

优化手段（组合使用）：
1. **只抽负评**：评分 ≤3 的才进 LLM（约占 20%），成本直接降到 ~$4.8k/年。
2. **批量发送**：10 条/请求，摊薄请求与模板开销，再降 ~30%。
3. **文本去重/缓存**：相同评价文本（模板化差评）命中缓存直接复用，免重复调用。
4. **分层模型**：先用小模型/规则做「是否值得抽」的二分类，命中才上大模型。
5. **采样审计**：绝大多数评价用规则标注，仅对长尾/低置信度样本抽样上 LLM。

> 成本意识是这道题高分点：10 万/天和 100 万/天的架构**不是同一套**——量级上升后必须引入「负评过滤 + 缓存 + 分层」，否则账单指数膨胀。

## 四、三个最大风险点与应对

**风险 1：LLM 延迟/成本尖刺**
评价突发（大促）时 LLM 调用激增，可能超 1min SLA 且账单暴涨。
应对：评价抽取走**异步队列**（非阻塞主流程），设超时与降级（超时转规则标注）；
对 LLM 调用做限流（token/s 配额）+ 熔断，异常时全量降级规则方法。

**风险 2：OLTP 与 OLAP 数据不一致**
卖家看「实时待发货」与「历史成交曲线」若口径不同会失去信任。
应对：以 MySQL 为唯一权威源，ClickHouse 通过 **CDC（如 Debezium）近实时同步**，
并对账任务每日校验行数/金额差异，超阈值告警。

**风险 3：事件丢失或重复（Kafka 语义）**
订单状态变更若丢失，卖家看不到；若重复，状态机错乱。
应对：生产者端开启 **acks=all + 幂等**，消费者端用 order_id+状态做**幂等写入**；
关键状态变更落地前先写 WAL/事务，保证 at-least-once + 去重 = effectively-once。

## 五、局限与预案（体现诚实）

- 本设计默认云原生组件；若团队无 Kafka 运维能力，可先用 **PostgreSQL + LISTEN/NOTIFY** 或
  **Redis Streams** 起步，待规模上来再迁移，避免过早复杂化。
- 6 个月曲线用 ClickHouse 预聚合（如按天物化），但「自定义时间粒度」的即席查询仍需保留原始明细表供下钻。
- 真实落地前必须做容量压测：在 100 万单/天目标下验证端到端 p99 延迟是否达标。
