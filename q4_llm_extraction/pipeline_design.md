# Q4 管道设计说明（pipeline_design.md）

## 一、分流策略（为什么不是全部丢给 LLM）

差评里大量是极短笼统词，如 `ruim`（差）、`péssimo`（极差），长度仅 2–5 个字符，
没有任何可抽取的事件信息。若全部送 LLM，既浪费 token 也无法产出有意义的 issue。
因此我做了两级分流：

1. **规则层**：长度 ≤4 或属于笼统负面词表的评价，直接用关键词规则归类
   （delivery_late / wrong_product / quality_defect …），severity 由评分决定，
   confidence 统一 0.5。这部分零成本、确定性强。
2. **LLM 层**：只有含实质内容的评价才进入大模型，且**批量（每批 10 条）发送**，
   把 N 次请求压成 N/10 次，显著降低调用开销与延迟。

## 二、Prompt 设计（防幻觉是核心）

- 强制 `evidence_quote` 必须是**原文真实子串**，并在规则里加断言校验，
  一旦发现抽取出的句子不在原文中即判定为幻觉。这比单纯"请基于原文"可靠得多。
- 类别用封闭枚举（7 类），避免模型自创标签导致下游无法聚合。
- `temperature=0` 保证结果可复现，便于面试复现与回归测试。
- 葡语处理：**直接让 LLM 输出 `evidence_quote_en` 英文翻译**，省去独立的翻译模型/API，
  既降成本又保证 quote 与翻译一一对应。

## 三、批量 vs 单条的成本权衡

单条请求有固定的请求开销与上下文重复；批量把 system/prompt 模板摊薄到多条评价上。
以 gpt-4o-mini 估算，1–2 万条差评全量 LLM 化约数美分~1 美元，远低于题目 $3 预算。
若预算进一步收紧，可把"规则层"的阈值调高，让更多简单差评走规则。

## 四、准确率如何验证（无 ground truth）

采用「自动结构校验 + 人工抽样 30 条对齐」：自动校验保证 JSON 合法、quote 为原文子串；
人工抽样按类别分层抽样 30 条，标注 category/severity 后计算一致率。
详细流程见 `accuracy_evaluation.md`。这套方法不依赖现成标注，且可重复执行。
